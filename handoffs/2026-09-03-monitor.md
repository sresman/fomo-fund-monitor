### Root cause

**Alerting had never delivered a single alert.** Not "broken since Aug 14" --
broken from the first post-seed run, `2026-08-10T00:01:11Z`, which produced 6
events and logged 6 failures. Proof independent of logs: `state/seen_filings.json`
was written exactly once in the repo's history (the 2026-08-09 seed) and never
again, and the orchestrator commits dedupe state only after a successful
dispatch.

The Gmail secrets were never set in GitHub Actions. That alone was recoverable;
what made it a 25-day silent outage was the reporting path:

1. `GmailSender` wrapped every transport exception in a constant-string
   `AlertError("email send failed")`, leaving the cause only on `__cause__`.
2. `Dispatcher` caught it into `DispatchResult.errors`.
3. `main.py` read `errors` **for truthiness only** and logged a content-free
   `alert failed for <id>`, then returned 0.

`grep '\.errors'` across production code returned exactly one hit -- that
truthiness test. Every run reported `conclusion: success`, so GitHub had nothing
to notify on. A total alerting outage and a transient blip were indistinguishable.

A second, independent defect was found during the same diagnosis: EDGAR spells
the Schedule 13D/G forms `"SCHEDULE 13G"` while config uses `"SC 13G"`, so
**every 13D/13G filing had been silently dropped by the tracked-form filter** --
including a SCHEDULE 13D disclosing a $523.9M / 21.1% position in SharonAI.

### Decisions made

Full log with rationale in `implementation-notes.md` (SD-A1 … SD-A55). The load-
bearing ones:

- **Alert set = first-party appearances (Baker or Leopold speaking) + SEC
  filings.** Everything else is captured silently. Google News was ~92% of
  volume; replaying the 2026-09-03T20:31Z run's mix through the new policy gives
  **153 events -> ~5 emails**.
- **Silence over disabling** for Google News: the dedupe bucket keeps accruing,
  so re-enabling is a one-line change with no backlog flood.
- **Channel allowlisting is the first-party test** for YouTube. Title framing no
  longer promotes to HIGH -- a title is written by whoever uploaded it.
- **`alert_delivered` distinguishes "routed nowhere" (commit) from "routed and
  nothing delivered" (outage, do not commit)**; they look identical in
  `channels_sent`, hence the new `DispatchResult.routed` field.
- **Fail loud raises at the END of the run**, so per-monitor isolation survives.
- **Every behaviour change was blast-radius-checked against real feed data
  first.** That discipline caught two of my own bugs before they shipped (below).

### Two bugs the tests had pinned as expected behaviour

Both are worth remembering, because in each case a green suite was actively
concealing a defect:

1. `test_real_manifest_has_zero_youtube_urls` asserted
   `load_manifest_youtube_ids(REAL_MANIFEST) == set()`, commented "the real
   manifest currently has ZERO YouTube urls". Every url in the file was an mp3 or
   a Colossus page, so **the YouTube dedupe source deduped nothing for the life of
   the repo**. Now generated from the corpus with `youtube_url` populated: 34 ids
   reaching dedupe, up from 0. Test inverted to a `>= 30` floor.
2. `test_high_surname_and_framing` asserted HIGH confidence for title
   `"Gavin Baker interview"` on channel `"Zzz"` -- the exact loophole by which a
   Chinese-language recap and two ~100-second clips reached the inbox. Inverted,
   with the three real uploads added as parametrised MEDIUM cases.
